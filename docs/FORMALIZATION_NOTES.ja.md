# F0.0 / F0.1 / F0.2 / F0.3 / F0.4 formalization notes

Draft 17.4をnormative source of truthとして維持し、変更していません。non-normative bridgeの編集修正は以下へ記録します。

- **FORMAL-EXTRACTION — F0.1前に解決**: 元のF0 Draft 0にあったmilestone番号の衝突を§20.2・§20.3・§24 traceability tableで修正し、§28へF0.6を追加しました。LifetimeDomain transfer/finalizationはF0.6、F0.2はstoreです。semantic ruleは変更していません。F0.0ではscope/roadmapの不一致として記録していた問題について、その履歴と解決を保持します。
- **FORMAL-ENCODING — F0.0から維持**: `RootLocationId → Occupancy`は同じPlaceIdと異なるcurrent factsを持つ二つのlocationを表せます。`PlacesUnique`によりこの不正stateを排除してWF-4を表現します。location-based carrierはpackageの二重installationも隠しません。F0.1のold-fact invalidation証明では、他rootが同じplaceのold factをliveに保つ可能性をplace uniquenessで排除します。
- **FORMAL-ENCODING — F0.0から維持**: F0 §4.2で許容されたPlaceId/RootLocationIdの同一視は採用せずnominalに分離しています。WellFormedなlive rootsのplace/location対応とincarnation identityの一意性をpredicateで表現します。
- **FORMAL-ENCODING — F0.1 history**: `usedValueFacts : Finset ValueFactId`はproof-only ghost stateです。`ValueFactsRecorded`はcurrent factを履歴へ含め、`FreshValueFact`は過去の割当てすべてを除外します。Raw replaceは新factをinsertし、retired factを削除しません。history monotonicityと、currently deadでもhistorically usedであり得るcountermodelを証明しました。初期状態には過去の履歴をすべて記録し、将来のallocating operationも履歴を拡張する必要があります。runtime/compilerのhistory storageは要求しません。F0.1当時はusedIncarnationsをF0.4へ保留し、今回以下のとおり実装しました。
- **FORMAL-LEMMA — F0.1 non-laundering**: Preservation theoremはlegal Stepのpost-state条件をprojectします。意味のあるnegative proofでは、raw candidateの具体的更新、old-fact invalidation、dependency dataの保存、old-package survivalを結合します。incoming caseも同じinvalidation lemmaを使います。すべてのraw candidateがWellFormedであるとは仮定しません。independentなlegal例でvacuityを排除し、dependency checkを省いたcountermodelでは他invariantがすべて成立することを確認しています。
- **FORMAL-ENCODING — F0.2 atomic consumption**: Storeは旧carrierを除去し、package tableの記録を残します。carrierのないdataはsurvivorではなく、runtimeでの物理削除やdestructor semanticsを要求しません。candidateは直接構成し、legal replaceを先に要求しません。旧値のdiscardabilityは既存Boolによるproof-side static abstractionで、runtime checkではありません。incomingのdiscardabilityはpremiseにしません。historical freshnessはF0.1から変更せず再利用します。
- **FORMAL-LEMMA — F0.2 survivorの区別**: Carrier uniquenessによりincoming = oldと旧値の二重installationを排除します。旧packageだけがsurviveせず、それ以外のsurvivorは追跡され続けます。old fact失効により第三survivor・incomingのdependencyは拒否します。同じ具体的pre-stateで、旧self-dependencyを持つreplaceは拒否・storeは合法と証明しました。dependency validationとdiscardability guardの必要性は独立したbreak-testで確認し、WellFormedだけではnon-discardable値のdiscardを許可できないことを示しました。
- **FORMAL-ENCODING — F0.3 case/freshness**: swap専用sumでsame-place（新fact引数なし・exact state identity）とdistinct-place（一つのatomic carrier exchange）を分離します。`FreshValueFactPair`は2つの未使用かつ互いに異なるIDを要求し、履歴を縮めず両方をinsertします。これは2つのfresh ghost allocationのproof encodingであり、runtime stampのglobal formatを要求しません。WellFormedにより異なるlocationsは異なるplacesで、carrier uniquenessからpackageの相違を導きます。package/dependency tableとplace-owned governing domainはexchange/retargetしません。
- **FORMAL-LEMMA — F0.3 non-laundering**: 両old factがdeadとなり、両packageと他survivorがsurviveします。通常のpost-state DependenciesValidでself/cross/cyclic/第三survivorのold-fact dependencyを拒否します。同じself-dependent pre-stateでsame-placeは合法・distinct-placeは拒否です。cyclic raw countermodelは他invariantをすべて満たし、independent legal witnessはnon-discardable packageと異なるgoverning domainsを使用します。Copy / Discardable requirementは追加しません。
- **FORMAL-ENCODING — F0.4 history extension**: Stateへproof-only usedIncarnations、WellFormedへIncarnationsRecordedを追加します。empty/既存candidate/fixtureを更新し、既存theorem statementやsemantic claimは弱めません。replace/store/same/distinct swapは履歴を完全保存します。LiveIncarnation / Governsはderived viewで、割当てはinitializeだけです。take/destroyはended incarnation/current factも履歴へ残します。
- **FORMAL-ENCODING — F0.4 typed sites**: Vacantはempty occupancy responsibilityの抽象化で、source-level slot value全体ではありません。実行proof contextのRootSiteLayoutでinjective location/place対応を固定し、initializeが参照します。同じsiteのreinitializeではplaceを保持しincarnation/current factをfreshenします。nominal型は分離し、fresh PlaceId allocationや追加global layout invariantは導入しません。F0 §4.2は対応encodingを許し、Draft 17.4 §14.1–2はtyped occupancy siteを保存します。fixtureのindex対応はnormative ID equalityやbacking geometryではありません。
- **FORMAL-LEMMA — F0.4 lifecycle/survivors**: initialize/takeはvacancyとunique carrierを保存し、same-site reinitializeは旧両IDを記録したまま新IDを使います。takeは旧survivorのself/third dependencyを拒否し、destroyはold-only dependencyを消費できてもthird survivorは拒否します。両方governing relationを終了しますがDomainLiveは保存します。domain equality / caller authorityは独立に検査し、discardabilityはapplicabilityでWellFormedへ入れません。
- **FORMAL-SCOPE — 残るscope**: 実装したoperationはreplace・store・swap・initialize・take・destroyです。borrow checker/type compatibilityのderivationはcallerが証明するProp premiseで、production側で常にTrueにはしません。exclusive/lifetime-ending authorityはreplace/store/swapへ要求しません。source-level ptr/ref/slot carrier、finite-support、payload/authority algebra、structural subobjects、scope/backing geometry、domain transfer/finalizationはscope外です。root-only restrictionはflat F0で構造的に成立します。initializeはordinary authorizationで、take/destroyは同じgoverning DomainIdへのabstract ending-authority proofを要求します。

F0.0/F0.1/F0.2/F0.3/F0.4で確認した関連節からFORMAL-HOLE / FORMAL-AMBIGUITYは発見していません。Draft 17.4の§13.5a・§17.4はstoreのatomic consumptionを明記しており、今回新たな抽出修正は不要でした。§17.4はsame-place no-opとdistinct-placeでのcomplete package / hidden dependency transferを明記し、§13.5aはexact fact identityとdependency survivalを規定します。2-fact pair allocationは上記のnon-normative encodingです。unchecked candidateは意図的break-testであり、normative legal operation ruleへの反例ではありません。Draft 17.4 §14.1–3もfresh start、same-site occupancy return、governing relation終了とdomain survivalの区別、atomic destroyを規定し、site/place表現は上記encoding choiceで解決しました。仕様全体のsoundnessも主張しません。
